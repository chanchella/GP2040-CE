# OAG SMART COMBO LOGIC V1

هذه إضافة مستقلة إلى نظام الكومبوهات الحالي. افتح رابط **OAG SMART COMBO LOGIC** من صفحة إعداد Wi-Fi أو المسار `/oag-smart`. النظام القديم وبياناته يظلان متاحين.

## أساس النسخة

السورس المتاح الذي بُنيت عليه هذه الإضافة هو `2c7434a772b498ee7a8d53b3d45d87defb0c5231` من `chatgpt/oag-f1-km-preserve-v2`. الفرع الذهبي لم يتغير. هوية البناء الجديدة `OAG-SMART-COMBO-LOGIC-V1-FIX2-BASE`.

ملف المستخدم الناجح `OAG_DIAMOND_RS8_PRO_INPUT_V1_F1_KM_FIX2_MOUSE_FIX1_Pico2W.uf2` محفوظ كمرجع عتادي منفصل، وSHA256 له `38ab5290aec6d3b59f5f64b023b2cf05e9409a28e3708e591f49bfa334728deb`. لم نعثر على السورس المطابق لتعديل MOUSE_FIX1؛ هذا البناء لا يدعي تضمينه، ولا يعد بديلًا عتاديًا معتمدًا لذلك المرجع قبل تجربة Pico. يمكن نقل الإضافة إلى سورسه حين يتوفر.

## الاستخدام

1. اختر اللعبة وخانة الكومبو، واكتب اسم OAG قصيرًا، ثم فعّل الكومبو.
2. اختر WHEN: زر وطريقة ضغط وتوقيت. أضف شروط AND / OR، أو NOT مع شرط موجب.
3. أضف خطوات THEN، واختر الأزمنة وعدد التكرارات. PRESS يثبت الناتج حتى RELEASE أو نهاية التنفيذ. HOLD بمدة موجبة يمسك ثم يفلت. HOLD بمدة صفر يثبت حسب العمر المحدد. RELEASE ALL يحرر ناتج هذا الكومبو وحده.
4. أضف ELSE IF أو ELSE / STOP، وحدد وضع التشغيل لكل فرع. الأولوية الإضافية اختيارية؛ عند التعادل تفصل درجة التحديد ثم ترتيب الخانة والفرع.
5. التعديلات تعرض في RAM بعد توقف التعديل قليلًا. اضغط SAVE لحفظ اللعبة على Pico. تغيير اللعبة مع تعديلات غير محفوظة يتيح حفظها أو إلغاءها أو البقاء.
6. Test Combo يحاكي خطوات الفرع المختار لمدة أقصاها خمس ثوانٍ، مع زر STOP. لا يرسل خرجًا فعليًا لأن Wi-Fi في هذا الـBaseline وضع إعداد منفصل عن اللعب وBluetooth. يجب اختبار التريجر الحقيقي في وضع اللعب بعد SAVE والخروج من الإعداد.

النظام يدعم 20 لعبة × 16 كومبو SMART. لكل كومبو حتى 4 فروع، ولكل فرع 4 شروط و16 خطوة. Chord / Sequence حتى 8 مدخلات، والخطوة حتى 4 أهداف معًا. يمكن تثبيت أهداف إضافية عبر خطوات PRESS متتالية. خرج الكيبورد يحافظ على حد USB الحالي: ستة مفاتيح عادية مع مفاتيح modifier.

كل أزرار Gamepad القديمة بمعرّفات 1..25 محفوظة، وتشمل الاتجاهات الثمانية للأنالوج الأيمن. أضيفت اتجاهات الأنالوج الأيسر 26..33 وShare بالمعرّف 34. مفاتيح HID 1..255، وmodifiers الثمانية E0..E7، وأزرار الماوس الستة عشر والعجلة متاحة. اختصارات النظام المحجوزة تظل لها الأولوية. إرسال KEY/MOUSE يحتاج وضع Native KM؛ خطوات Gamepad تستخدم مسار الخرج الحالي.

## قواعد الضغط والتوقف

- Single / Double / Triple / Multi تعد ضغطات مكتملة، وتنتظر أكبر نافذة للشروط المنافسة على نفس المدخل. لا يبدأ Single مبكرًا. النافذة تبدأ عند الضغط الأول، ويجب أن تكون آخر ضغطة ضمن نافذة الفرع نفسه.
- Long / Hold يحدثان مرة عند بلوغ العتبة. الفوز بهما أو بـChord أو Sequence يمنع إعادة تشغيل التريجر الفردي من نفس الحركة.
- Chord يتطلب أن تكون الأزرار كلها مضغوطة وأن تكون أوقات ضغطها ضمن Chord Window. Sequence يتتبع الخانات بالترتيب، ويتيح تكرار الزر، والمهلة من أول خطوة. ضغط زر آخر من أزرار السلسلة يعيد التعرف عليها؛ الأزرار خارجها لا تدخل في التعرف.
- AND له أولوية على OR. NOT ينفي نتيجة الشرط، لذلك Held / Threshold مفيدان للشروط النافية. الإمساك المشترك وحده لا يمنع فرعين لهما أحداث تفعيل مختلفة.
- Run While Held / Repeat While Held / Stop On Release تتبع حالة WHEN الفعلية؛ استخدم Held أو Long / Hold معها. Trigger من نوع Tap يتعرف بعد الإفلات، ولذلك لا يبقى ممسوكًا عند انتهاء نافذته.
- Toggle ينفذ مرة ويبقي التثبيت حتى التفعيل الثاني. Loop Until Triggered Again يكرر حتى التفعيل الثاني. Cancelable يسمح للتفعيل الجديد بإلغاء التنفيذ الجاري وبدء الفرع الجديد. STOP ينهيه ويفلت الناتج.
- عند مشاركة مدخل موجب مع كومبو قديم، تكون الأولوية لـSMART، ويُحجب الكومبو القديم الذي يشارك المدخل خلال تفعيل تعريف SMART. التعطيل يعيد القديم. هذا الحجب يشمل الخانة القديمة كاملة إذا كان أحد تريجراتها مشاركًا؛ بياناتها محفوظة.

## المعمارية ومساحة البيانات

| طبقة | ملفات | مسؤولية |
|---|---|---|
| نموذج مستقل | `config/smart_combo_config.*` | أنواع وقيود وCRC مستقل؛ دون تعديل السجل القديم |
| تحكم ومنطق | `mapping/smart_combo_controls.*`, `smart_combo_engine.*` | التعرف والتحكيم والتنفيذ بوقت مورّد من المستدعي؛ دون نقل أو Flash |
| توافق | `mapping/smart_combo_legacy.*` | تحديد الكومبوهات القديمة التي تشارك تريجر SMART |
| تخزين | `firmware/smart_combo_store.*` | لعبة واحدة في RAM، ونسختا A/B لكل لعبة، وSAVE فقط |
| بوابة | `firmware/smart_combo_portal.*` | تحميل ومعاينة ذرية متعددة الأجزاء، وحفظ ومحاكاة |
| واجهة | `tools/smart_ui_assets/*` | المنشئ العربي؛ `embed_smart_ui.py` يولد الهيدر |
| ربط محدود | `main.cpp`, `diamond_wifi_portal.*`, `diamond_combo_engine.*`, CMake | نقطة ما بعد mapping، وخط الزمن، ودمج الناتج في Native KM، ومسارات الواجهة |

التخزين الجديد أسفل منطقة الألعاب القديمة. عند Pico 2 W ذي 4 MiB واحتياطي RP2350 A2 يبدأ SMART عند offset **1,150,976**. مساحة كل نسخة 57,344 بايت؛ مجموع 20 لعبة × نسختين 2,293,760 بايت. لا تتغير عناوين config أو الألعاب القديمة أو Bluetooth أو القطاع الأخير. `ready()` يعطل الإضافة وحدها إذا اقترب كود firmware من منطقة SMART.

لا يكتب SMART عند الإقلاع أو التعديل أو تغيير اللعبة. SAVE يمسح النسخة الأقدم فقط، ويبرمج السجل من RAM مع حشو الصفحة الأخيرة، ثم يتحقق من CRC. نسخة سليمة سابقة تبقى عند انقطاع كتابة الجديدة. لا يحفظ تعريفًا نصف مكتمل: begin → كل أجزاء الفروع → تحقق → preview؛ مع revision/token ومدة صلاحية محددة.

وضع إعداد Wi-Fi ووضع اللعب منفصلان كما في الـBaseline. يشتركان في محرك SMART ونسخة اللعبة لتجنب تكرار RAM؛ لا يُدّعى دعم تعديل متزامن أثناء اللعب. خط الزمن كل 1 ms، والمفسر محدد بعدد خطوات لكل استدعاء، دون sleep. القراءة فقط عند تبديل اللعبة؛ CRC يستخدم جدولًا ثابتًا في Flash لتقليل زمن القراءة.

## التحقق وإعادة البناء

```sh
python3 oag/tools/check_architecture.py
node oag/tools/test_combo_editor.js
python3 oag/tools/embed_smart_ui.py --check
cmake -S oag -B build/oag-host -DCMAKE_BUILD_TYPE=Debug
cmake --build build/oag-host --parallel 2
ctest --test-dir build/oag-host --output-on-failure
PLAYWRIGHT_MODULE=/path/to/playwright node oag/tools/test_smart_ui.mjs
```

اختبارات SMART تغطي ضغطات التوقيت، الأسبقية، AND/OR/NOT، الفروع وELSE، طرق التوقف، التكرار، العجلة، الأنالوج وKEY/MOUSE، عزل اللعبة، عدم الكتابة مع preview، حفظ A/B واستعادة الكتابة الناقصة، ومعاملات HTTP الجزئية والقديمة. اختبار المتصفح يستخدم API C++ الحقيقي بمحاكاة Flash، ويتحقق من التحكم والحفظ والنسخ والحذف وعزل اللعبة وتخطيط الهاتف.

لبناء العتاد استخدم نفس Pico SDK `98a542c1a62fb549ffb5d66a3e5892b06276b670` وTinyUSB `9865cba11ecbcdd25237ba9cf4ccbe3fd1fd821d` وPIO USB `5a37a66dc5d3fbe0ef3cdbeda923a757440f984f`، ثم `prepare_dependencies.py` الحالي دون تغيير ترقيعاته. CI الخاص بالفرع ينفذ الاختبارات ثم يبني UF2 ويحتفظ بملف MAP وELF. نجاح البناء واختبارات المضيف لا يثبت استقرار Bluetooth/USB/rumble فعليًا على الجهاز؛ تجربة Pico قبل اعتبار هذا الفرع Stable ما زالت مطلوبة.

الرجوع إلى UF2 السابق لا يمس بيانات legacy لأن عناوينها ثابتة. احتفظ بالملف العتادي الناجح ولا تستخدم Flash Nuke، الذي يمسح البيانات. منطقة SMART المنفصلة قد تبقى بعد الرجوع، ولا يقرأها الـBaseline القديم.
